## 1. 防超卖 — Redis Lua 原子锁

### 1.1 问题背景：为什么会超卖？

**超卖**：商品实际库存只有 10 件，但卖出去了 15 件。

**根本原因**：「查库存」和「扣库存」是两步操作，多线程并发时中间会被打断。

```
线程A：查库存 = 10 ✓ → （还没扣减，被线程B抢占）
线程B：查库存 = 10 ✓ → 扣减 → 库存 = 9
线程A：继续扣减 → 库存 = 8  ← 两个人都买到了，但只扣了2件，逻辑正确
```

但高并发时 1000 个线程同时查到库存=10，全部认为"有货"，全部下单，就超卖了。

**危害：**
| 危害 | 具体表现 |
|------|----------|
| 商品发不出去 | 卖了100件，仓库只有10件，缺货90件 |
| 客诉与退款 | 大量用户付款后被告知缺货，需退款赔偿 |
| 资金损耗 | 赔偿优惠券、人工处理成本 |
| 品牌信誉 | 社区小店口碑受损，碧桂园旺生活用户流失 |

---

### 1.2 解决方案：Redis Lua 脚本原子操作

**核心思想**：把「检查库存」和「扣减库存」合并成**一个原子操作**，Redis 单线程执行 Lua 脚本，中间不会被打断。

#### Lua 脚本内容（`inventory_lock.lua`）

```lua
-- KEYS[1] = "inventory:sku:1001"  (Redis中库存的Key)
-- ARGV[1] = "2"                   (需要扣减的数量)

local stock = redis.call('GET', KEYS[1])

-- 情况1：Redis中没有这个Key（库存未预热到缓存）
if stock == false then
    return -2   -- 告诉Java层：缓存未预热，走DB查询
end

-- 情况2：库存不足
if tonumber(stock) < tonumber(ARGV[1]) then
    return -1   -- 告诉Java层：库存不足，拒绝下单
end

-- 情况3：库存足够，原子扣减
return redis.call('DECRBY', KEYS[1], tonumber(ARGV[1]))
-- 返回扣减后的剩余库存数，例如返回 8（扣了2件，原来10件）
```

**返回值含义：**
| 返回值 | 含义 | Java层处理 |
|--------|------|-----------|
| `-2` | 缓存未预热 | 从DB查库存，写入Redis，重试 |
| `-1` | 库存不足 | 返回"库存不足"给前端 |
| `≥ 0` | 扣减成功 | 继续异步落库流程 |

---

### 1.3 时序图

```
用户下单(买2件SKU-1001)
        │
        ▼
  FulfillmentService.submit()
        │
        ▼
  执行 Lua Script (原子操作，不可分割)
  ┌─────────────────────────────────────┐
  │  GET inventory:sku:1001  →  10     │
  │  10 >= 2 ? YES                     │
  │  DECRBY inventory:sku:1001 2       │
  │  返回 8                             │
  └─────────────────────────────────────┘
        │
   返回 8 (>=0 说明成功)
        │
        ├──→ 发送 Kafka消息 inventory.deduct (异步落DB)
        │
        └──→ 返回下单成功给用户

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

同时有1000个并发请求 (只有10件库存)
        │
     Redis单线程队列
        │
  请求1：GET=10, DECRBY 2 → 返回8 ✓
  请求2：GET=8,  DECRBY 2 → 返回6 ✓
  请求3：GET=6,  DECRBY 2 → 返回4 ✓
  请求4：GET=4,  DECRBY 2 → 返回2 ✓
  请求5：GET=2,  DECRBY 2 → 返回0 ✓ (最后一件)
  请求6：GET=0,  0 < 2    → 返回-1 ✗ (库存不足)
  请求7～1000：全部返回-1  ✗

结果：精确卖出5笔×2件=10件，无超卖 ✅
```

### 1.4 真实数据示例

**Redis 中的数据：**
```
Key:   inventory:sku:1001
Value: 10
TTL:   86400秒 (1天)

Key:   inventory:sku:1001:locked   ← 预锁定量（下单未付款的）
Value: 3
```

**Java 代码调用：**
```java
// 调用Lua脚本扣减库存
Long result = redisTemplate.execute(
    inventoryLockScript,                    // Lua脚本Bean
    List.of("inventory:sku:1001"),          // KEYS
    String.valueOf(2)                       // ARGV：扣减数量
);

if (result == -2L) {
    // 缓存击穿，从DB预热后重试
    warmUpInventoryCache(skuId);
    return submitOrder(skuId, qty);  // 重试一次
} else if (result == -1L) {
    throw new SupplyChainException("库存不足");
} else {
    // result = 8, 预扣成功
    sendKafkaDeductMsg(orderId, skuId, qty);
}
```

## 2. FIFO 批次出库 — 先进先出保鲜保质

### 2.1 问题背景：为什么需要 FIFO？

**场景**：生鲜商品（蔬菜、牛奶、水果）按批次入库，不同批次有不同的生产日期和到期日。

**不用 FIFO 的危害：**
| 问题 | 具体表现 |
|------|----------|
| 先入后出（LIFO） | 新货不断被卖，旧货积压在仓库里慢慢过期 |
| 随机出库 | 客户收到距离过期只剩2天的牛奶，投诉率飙升 |
| 库存损耗 | 过期商品只能报废，直接财务损失 |
| 食品安全 | 过期商品流入市场，引发监管问题 |

**真实案例**：牛奶保质期30天，仓库同时有3个批次：
- 批次A：2026-05-01 入库，到期 2026-05-31（还剩3天）
- 批次B：2026-05-15 入库，到期 2026-06-14
- 批次C：2026-05-25 入库，到期 2026-06-24

**错误（LIFO）**：先出C → B → A（A批次到期报废）  
**正确（FIFO）**：先出A → B → C（零报废）

---

### 2.2 实现方式

#### 数据库批次表设计

```sql
CREATE TABLE sc_inventory_batch (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    sku_id        BIGINT NOT NULL,
    warehouse_id  BIGINT NOT NULL,
    batch_no      VARCHAR(64) NOT NULL,      -- 批次号，如 BATCH-20260501-001
    inbound_qty   INT NOT NULL,              -- 入库数量
    available_qty INT NOT NULL,              -- 当前可用数量
    inbound_time  DATETIME NOT NULL,         -- 入库时间（FIFO排序依据）
    production_date DATE,                    -- 生产日期
    expiry_date   DATE NOT NULL,             -- 到期日期
    batch_status  TINYINT DEFAULT 0          -- 0正常 1临期 2紧急 3已过期
);
```

#### FIFO 查询（关键 SQL）

```java
// InventoryBatchMapper.xml
// 按入库时间升序查，只查有剩余库存的批次
List<InventoryBatch> selectFifoBatches(
    @Param("skuId")       Long skuId,
    @Param("warehouseId") Long warehouseId,
    @Param("totalQty")    Integer totalQty
);
```

```sql
SELECT * FROM sc_inventory_batch
WHERE sku_id = #{skuId}
  AND warehouse_id = #{warehouseId}
  AND available_qty > 0
  AND batch_status != 3        -- 排除已过期
ORDER BY inbound_time ASC      -- ← 关键：最早入库的排最前
LIMIT 10                       -- 最多取10个批次
```

#### 跨批次分配逻辑（`allocateFifo`）

```
场景：用户买 25 件牛奶

批次列表（FIFO顺序）：
  批次A: available_qty = 10, inbound_time = 2026-05-01
  批次B: available_qty = 8,  inbound_time = 2026-05-15
  批次C: available_qty = 20, inbound_time = 2026-05-25

分配过程：
  需要: 25件
  从批次A扣: min(10, 25) = 10件, 剩余需求: 25-10 = 15件, 批次A剩余: 0
  从批次B扣: min(8,  15) = 8件,  剩余需求: 15-8  = 7件,  批次B剩余: 0
  从批次C扣: min(20, 7)  = 7件,  剩余需求: 7-7   = 0件,  批次C剩余: 13件

结果：
  批次A出 10件（全部清空，最老库存优先出）✅
  批次B出 8件  （全部清空）✅
  批次C出 7件  （还剩13件）✅
```

---

### 2.3 时序图

```
用户下单25件牛奶(SKU-2002, 仓库W01)
        │
        ▼
  InventoryService.allocateFifo()
        │
        ▼
  DB查询: SELECT * FROM sc_inventory_batch

```

## 3. 异步落库 — Kafka + 重试 + 死信队列

### 3.1 问题背景：为什么要异步？

**同步方案的问题**：

```
用户下单 → Redis预扣(1ms) → 写MySQL(20ms) → 返回成功
                              ↑
                         这20ms是瓶颈！
高并发时MySQL写操作堆积，响应变慢，甚至超时
```

**如果直接同步写DB：**
| 问题 | 影响 |
|------|------|
| MySQL写TPS有限（约2000/s） | 高峰期下单失败率上升 |
| 写DB耗时20~50ms | 接口响应慢，用户体验差 |
| DB宕机影响下单 | 可用性降低 |

**解决思路**：Redis预扣保证不超卖（毫秒级），然后用Kafka异步把扣减结果写进MySQL，两者解耦。

---

### 3.2 完整流程

#### 消息格式

```json
{
  "eventType": "INVENTORY_DEDUCT",
  "orderId": "ORDER-20260528-00001",
  "skuId": 1001,
  "warehouseId": 1,
  "qty": 2,
  "timestamp": "2026-05-28T10:30:00",
  "traceId": "abc123"
}
```

#### Kafka Topic 设计

| Topic | 用途 | 分区数 | 消费者组 |
|-------|------|--------|----------|
| `inventory.deduct` | 库存扣减 | 8 | `inventory-deduct-group` |
| `inventory.restore` | 库存还原（取消订单） | 8 | `inventory-restore-group` |
| `inventory.confirm` | 出库确认（发货完成） | 4 | `inventory-confirm-group` |
| `inventory.deduct.DLT` | 扣减死信队列（处理失败） | 4 | `inventory-dlt-group` |

---

### 3.3 时序图

```
用户下单
  │
  ▼
FulfillmentService
  │
  ├─1─→ Lua Script: Redis预扣 (1ms) ← 原子，不会超卖
  │      返回剩余库存=8
  │
  ├─2─→ 插入 sc_fulfillment_order (DB, 订单记录)
  │
  ├─3─→ 发送 Kafka: inventory.deduct
  │      {"orderId":"xxx", "skuId":1001, "qty":2}
  │
  └─4─→ 立即返回"下单成功"给用户 ✅ (总耗时约5ms)

                ↓ 异步 (约100~500ms后)

  InventoryListener.onDeductMessage()
  │
  ├─A─→ 查询 sc_inventory (DB) 当前库存
  ├─B─→ UPDATE sc_inventory SET available_qty = available_qty - 2
  ├─C─→ INSERT sc_inventory_log (操作流水)
  └─D─→ 提交Kafka Offset ✅

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

失败重试机制：

  第1次消费失败 (DB超时)
       │ 等待 1秒
  第2次重试失败
       │ 等待 2秒
  第3次重试失败
       │
       ▼
  发送到 inventory.deduct.DLT (死信队列)
       │
       ▼
  DLT监听器：
    ├── 发送告警(钉钉/短信)
    ├── 记录日志
    └── 人工介入 or 补偿任务处理
```

---

### 3.4 取消订单还原库存

```
用户取消订单
  │
  ▼
FulfillmentService.cancel()
  │
  ├─1─→ UPDATE sc_fulfillment_order SET status='CANCELLED'
  │
  ├─2─→ Redis INCRBY inventory:sku:1001 2  (还原Redis缓存)
  │
  └─3─→ 发送 Kafka: inventory.restore
         {"orderId":"xxx", "skuId":1001, "qty":2}

                ↓ 异步

  InventoryListener.onRestoreMessage()
  └── UPDATE sc_inventory SET available_qty = available_qty + 2
```

---

### 3.5 为什么要有死信队列（DLT）？

**没有DLT的问题**：消费失败后不断重试，堵塞整个消费者，后续所有消息都卡住。

**DLT解决了什么**：
- 隔离"毒消息"（坏数据），不影响正常流程
- 保留现场数据，支持人工排查
- 支持后续补偿处理（凌晨对账会发现差异并修复）

## 4. 定时对账 — Redis vs DB 凌晨全量校验

### 4.1 为什么需要对账？

异步架构的代价：**Redis（缓存）和 MySQL（持久化）可能出现数据不一致**。

**什么情况会不一致？**

| 场景 | 原因 |
|------|------|
| Kafka消费延迟 | Redis已扣减，DB还没更新 |
| Kafka消费失败进DLT | Redis扣了，DB没扣 |
| Redis宕机重启 | 缓存数据丢失，预热不完整 |
| 业务BUG | 某些场景下Redis和DB操作顺序出错 |
| 并发边界情况 | 极端并发下的竞态条件 |

**危害：**
| 问题 | 影响 |
|------|------|
| Redis显示有货但DB是0 | 用户买到货但发不出去（超卖） |
| DB有货但Redis是0 | 商品明明有货却显示售罄（少卖，损失GMV） |
| 长期不对账 | 差异越来越大，财务报表失准 |

---

### 4.2 对账流程

```
凌晨 02:00 InventoryReconcileJob 触发
  │
  ▼
查询 sc_inventory (DB) 所有 SKU 库存
  │
  ▼
循环每个 SKU：
  │
  ├── 读 Redis: GET inventory:sku:{skuId}
  │
  ├── 比较：
  │   DB.available_qty = 10
  │   Redis.value      = 8   ← 差2件！
  │
  ├── 以 DB 为准（DB是事实来源）：
  │   SET inventory:sku:{skuId} 10   (修复Redis)
  │
  └── 写对账流水：
      INSERT sc_inventory_log
      (sku_id=1001, op_type=RECONCILE,
       before_qty=8, after_qty=10, diff=+2,
       remark="凌晨对账修复")
  │
  ▼
生成对账报告：
  - 总SKU数: 1580
  - 一致: 1576
  - 不一致: 4 (已修复)
  - 修复总差异量: +7件
```

---

### 4.3 时序图

```
02:00:00  InventoryReconcileJob.run()
    │
    ├── SELECT * FROM sc_inventory  →  [1580条记录]
    │
    ├── 遍历每条记录 (批量GET减少Redis请求):
    │     MGET inventory:sku:1001
    │          inventory:sku:1002
    │          inventory:sku:1003 ...
    │
    ├── 逐一对比：
    │     SKU-1001: DB=10, Redis=10  → 一致 ✅
    │     SKU-1002: DB=5,  Redis=3   → 差2件 ⚠️
    │     SKU-1003: DB=0,  Redis=nil → Redis未预热 ⚠️
    │     SKU-1004: DB=20, Redis=20  → 一致 ✅
    │
    ├── 修复不一致项:
    │     SET inventory:sku:1002 5   (以DB为准)
    │     SET inventory:sku:1003 0   (预热)
    │
    ├── 批量写对账日志
    │
02:00:45  对账完成，耗时45秒
    │
    └── 发送日报通知（如有差异超过阈值，触发告警）
```

---

### 4.4 为什么以 DB 为准？

```
Redis 是缓存，不是数据源：
  - Redis 可能因 OOM、重启、网络分区 丢失数据
  - DB 有 WAL 日志、主从复制、数据持久化
  - DB 的数据才是"合同级别"的准确数据

口诀：缓存是加速层，DB是真理层。
      有冲突，DB说了算。
```

## 5. 效期四级预警 — 生鲜有效期管理

### 5.1 问题背景

生鲜商品（蔬菜、水果、乳制品、肉类）有保质期，需要提前预警采取行动，否则：

| 问题 | 影响 |
|------|------|
| 过期未发现 | 过期商品发给用户，食品安全事故 |
| 临期未处理 | 打折促销机会损失，最终报废 |
| 大量报废 | 直接财务损失（生鲜损耗率是KPI） |
| 补货不及时 | 畅销商品断货，用户体验差 |

---

### 5.2 四级状态设计

| 状态等级 | 英文枚举 | 触发条件（剩余天数） | 处理动作 |
|---------|----------|-------------------|---------|
| 🟢 正常 | `NORMAL` | > 7天 | 无需处理 |
| 🟡 临期 | `NEAR_EXPIRY` | 4~7天 | 系统通知仓管，建议移出优先销售位 |
| 🔴 紧急 | `URGENT` | 1~3天 | 自动触发促销打折，Kafka通知营销系统 |
| ⚫ 已过期 | `EXPIRED` | ≤ 0天 | 立即锁定批次，禁止出库，通知报废处理 |

---

### 5.3 时序图

```
每天 08:00:00  ExpiryWarningJob.run()
    │
    ├── 查询所有未过期且有库存的批次：
    │   SELECT * FROM sc_inventory_batch
    │   WHERE available_qty > 0
    │     AND batch_status != 3  -- 排除已知过期
    │
    ├── 遍历每个批次，计算剩余天数：
    │   剩余天数 = expiry_date - TODAY
    │
    │   批次A: expiry=2026-05-29, 今天=2026-05-28, 剩余=1天
    │     → URGENT (紧急)
    │     → UPDATE batch_status = 2
    │     → INSERT sc_expiry_warning (预警记录)
    │     → 发 Kafka: expiry.warning
    │       {"batchId":101, "skuId":1002, "level":"URGENT",
    │        "expiryDate":"2026-05-29", "qty":50}
    │
    │   批次B: expiry=2026-05-27, 今天=2026-05-28, 剩余=-1天
    │     → EXPIRED (已过期)
    │     → UPDATE batch_status = 3
    │     → UPDATE available_qty = 0 (锁定，禁止出库)
    │     → 发 Kafka: expiry.warning (level=EXPIRED)
    │
    │   批次C: expiry=2026-06-03, 今天=2026-05-28, 剩余=6天
    │     → NEAR_EXPIRY (临期)
    │     → INSERT sc_expiry_warning
    │
    └── 08:02:30 扫描完成，处理 1580 个批次

                ↓ Kafka 消费者处理

    ExpiryWarningListener:
      NEAR_EXPIRY → 发送站内消息给仓管 + 记录日志
      URGENT      → 调用营销系统API打8折促销 + 发钉钉告警
      EXPIRED     → 创建报废工单 + 通知仓管盘点 + 同步金蝶做账
```

## 7. 面试高频问题 Q&A

### 🔴 防超卖相关

**Q1：为什么用 Lua 脚本而不是 Redis 事务(MULTI/EXEC)？**

> A：Redis 事务是乐观锁，watch-multi-exec 模式下如果 key 被修改会整体放弃，需要重试，高并发下重试风暴严重。Lua 脚本是真正的原子操作，Redis 单线程执行期间不会被打断，没有重试问题，性能更好。

**Q2：Lua 脚本返回 -2（缓存未预热）你怎么处理？**

> A：捕获 -2 后，从 DB 查询 `sc_inventory.available_qty`，用 `SET key value EX 86400` 写入 Redis（加随机TTL防止缓存雪崩），然后重试一次 Lua 脚本。注意要加分布式锁防止并发时多个线程同时预热，用 `SET key value NX EX 5`（NX=不存在才写）实现。

**Q3：Redis 库存是 -1 了（扣过头了）怎么回事？**

> A：正常情况 Lua 脚本会保护，不会出现 -1。如果出现，肯定是有地方绕过了 Lua 直接调用了 DECR，或者对账 Job 的修复逻辑有 bug。这也是凌晨对账的价值，第二天早上对账会发现并修复。

---

### 🟡 FIFO 相关

**Q4：FIFO 是在 Redis 里做还是在 DB 里做？**

> A：在 DB 里做。批次分配（allocateFifo）是业务逻辑，用 SQL `ORDER BY inbound_time ASC` 取最老批次，在 Java 层循环分配数量。Redis 只存 SKU 总库存（用于预扣防超卖），不存批次明细（因为批次数据量大、更新频繁，缓存意义不大）。

**Q5：一个 SKU 有几百个批次，FIFO 查询会不会慢？**

> A：加复合索引 `(sku_id, warehouse_id, inbound_time, batch_status)` + `available_qty > 0` 过滤，实测百万级批次数据下查 10条 约 5~10ms。此外，`LIMIT 10` 限制最多处理 10 个批次，超过说明库存管理有问题，应该先做批次清理。

---

### 🟢 异步落库相关

**Q6：Redis 预扣成功，但 Kafka 消息发送失败了，库存不一致怎么办？**

> A：两道保障：① Kafka 发送用 `send().get()` 同步等待 broker 确认（加超时），发送失败抛异常回滚订单，Redis 还原库存。② 即使消息丢失进了 DLT，凌晨对账会以 DB 为准修复 Redis（DB还没减，Redis已减，对账后把 Redis 加回来）。

**Q7：Kafka 消费端幂等性怎么保证？一条消息被消费两次怎么办？**

> A：每条消息携带 `orderId` + `eventType` 作为唯一键，消费前查 `sc_inventory_log` 是否已有相同 `(order_id, op_type)` 的记录，有则跳过（幂等）。DB 层也加唯一索引 `UNIQUE KEY uk_order_op (order_id, op_type)` 作为兜底。

**Q8：为什么重试 3 次而不是无限重试？**

> A：无限重试会导致消费者线程全部堵在失败消息上，后续正常消息无法消费，整个库存系统瘫痪。3次重试后进 DLT，DLT 有专门的监控和告警，再 + 凌晨对账双重兜底，可靠性已经足够。

---

### 🔵 对账相关

**Q9：凌晨扫描 1000+ SKU，对账期间有人下单怎么办？**

> A：对账是"最终一致性"设计，不加全局锁。对账只做修复动作（SET Redis=DB值），即使修复过程中有新扣减，修复的值可能不完全准确，但下一次对账（明天凌晨）会再次修正。生产环境中凌晨 2 点流量极低，影响面很小。如果业务要求更高一致性，可以改成分段对账（每 10 分钟对账一部分）。

**Q10：为什么以 DB 为准而不是以 Redis 为准？**

> A：Redis 是缓存，设计上允许数据丢失（重启、OOM都会丢）。MySQL 有 binlog、主从复制、数据持久化，是"真理数据源"（Source of Truth）。缓存永远服务于数据库，数据库说多少就是多少。

---

### 🟠 效期预警相关

**Q11：效期预警触发促销打折，如果营销系统挂了怎么办？**

> A：效期预警通过 Kafka 发事件（`expiry.warning`），营销系统作为 Kafka 消费者处理。供应链中台只负责"发通知"，不关心营销系统是否成功执行，做到职责解耦。营销系统有自己的重试和补偿机制，预警记录也落了库（`sc_expiry_warning`），便于人工补操作。

**Q12：同一批次明天又被扫到怎么办？会重复预警吗？**

> A：`sc_expiry_warning` 有 `(batch_id, warning_date)` 联合唯一索引，同一批次同一天只插入一次。Job 扫描前也会检查当天是否已预警，幂等处理。

---

### ⚡ 综合设计问题

**Q13：整套方案最大的风险点是什么？**

> A：**Redis 和 DB 短暂不一致窗口**。从 Redis 预扣到 Kafka 消费落 DB，中间有 100ms~500ms 窗口，如果这期间有人查 DB 库存会看到"旧值"（偏高）。解决方案：① 前端库存查询优先走 Redis；② 如需强一致性（如财务对账），走 DB；③ 凌晨全量对账保底。

**Q14：这套架构能支撑多大的并发量？**

> A：Redis 单机 QPS 10万+，Lua 脚本原子操作约 5~8 万 QPS；Kafka 8 分区理论消费 TPS 约 8000~16000/s；MySQL 写 TPS 约 2000~5000/s（对账用）。整体架构支撑峰值 **5 万 QPS** 下单无压力，符合旺生活社区 O2O 大促场景（社区级流量）。

**Q15：你在这个项目里负责什么，遇到最难的问题是什么？**

> A（参考答法）：核心负责供应链中台的设计与实现，包括商品中心 SPU/SKU 多级属性、分布式库存防超卖、FIFO 批次管理、效期预警四级体系。
>
> 最难的是「Redis 预扣 + Kafka 异步落库」的**一致性设计**。早期测试时发现 Kafka 消费端偶发重复消费（Kafka At-Least-Once 语义），导致同一个订单库存被扣两次。最终方案是：消费端加幂等检查（查已有日志流水）+ DB 唯一索引兜底 + 凌晨对账修复残留差异，三层保障解决这个问题。
